# 1.4.1 图片下载诊断与重试计划（已确认）

## 目标与证据边界

执行 9235 已定位，但原始结果 URL、下载状态码和底层异常未保存，不能认定失败根因就是网络波动。1.4.1 的目标是使下一次失败可诊断、已生成的结果可恢复下载，并缓解暂时性下载失败。

## 方案比较

1. 推荐：保留 n8n HTTP 下载工具，补齐诊断、增加有界的纯下载重试。兼容现有网络设置，改动集中。
2. 仅补齐诊断：改动最少，但暂时性失败仍会直接中断执行。
3. 改用原生 HTTPS 或双下载实现：目前没有证据证明更稳定，会额外引入代理、重定向和安全策略兼容成本，暂不采用。

## 建议设计

### 1. 将错误按阶段分类

- 生图请求、响应解析、URL 校验、图片下载、格式识别、Binary 输出分别保留明确的阶段信息。
- 明确区分生图 HTTP 状态和下载 HTTP 状态；没有收到下载响应时不填造状态码。
- 下载失败记录异常类型/代码、每次尝试耗时、已知 HTTP 状态、Content-Type、已知响应字节数、结果域名。
- 保留生图请求 ID；如下载服务返回可用的追踪 ID，则单独保存。
- 错误示例：生图 HTTP 200；下载尝试 3/3 失败，ECONNRESET，未收到 HTTP 响应。不会重新发起生图。
- 图片格式错误仅描述实际识别结果，不把 Content-Type 或文件头识别等同于完整文件有效性校验。

### 2. 保留失败结果的下载依据

- 当响应包含结果 URL 时，后续失败的执行错误详情仍需保留 `imageUrl`、生成请求 ID、失败阶段及下载尝试记录。
- 使用 n8n 可序列化的错误详情/上下文，并验证信息在数据库和错误详情 UI 中实际保留；不能只留在内存或控制台。
- 沿用成功输出 `binary.data` 与 `json.imageUrl`。
- 默认下载失败仍报错，避免下游将缺少 Binary 的结果误当成功。
- 保持 `continueOnFail` 的原有语义，同时保留诊断及恢复下载字段和输入 item 关联。
- 完整签名 URL 仅进入用户自己的执行详情，不放入普通容器日志。日志不记录 API Key、Authorization、完整签名参数、提示词或 Base64；不直接输出 Axios 错误对象和响应原文。
- 恢复时可复制结果 URL 到独立 HTTP Request 下载节点，无需重新生成。
- 本版本不新增下载专用模式或持久化图片缓存。

### 3. 有界的纯下载重试

- 最多 4 次下载尝试（首次 + 最多 3 次重试），始终使用同一结果 URL，不重新调用生图/编辑 POST。
- 对超时、连接中断、临时 DNS 错误、HTTP 408/429/500/502/503/504 等暂时性错误重试。
- 无效 URL、明确的权限/签名错误、404、证书校验失败和已确认的 HTML/JSON 非图片响应不盲目重试。
- 建议单次下载上限 20 秒，累计下载预算不超过 80 秒；使用剩余预算约束每次请求与等待。与现有生图请求超时分开管理。
- 三次重试基础等待为 2 秒、5 秒、10 秒，增加少量随机扰动；429/503 如带 Retry-After，则在剩余预算内等待，超预算停止。
- 用户取消后停止等待和后续尝试，按运行时能力沿用 n8n 的取消机制。
- 1.4.1 先使用内部默认值，不增加多个调优参数。

### 4. 明确整体自动重试边界

- 内部下载重试只能保证一次节点调用内不重复生成。n8n 的 retryOnFail、手动重跑和重新执行工作流仍可能重新发起生成。
- 在 GPT 图像模式说明及 README 中提示：使用内部下载重试，关闭整个生图节点的失败自动重试；失败后通过已保存 URL 恢复下载。
- 不擅自修改用户工作流配置，也不承诺跨执行的自动去重。

### 5. CI 和版本文档

- 修复已确认的隐藏视频选项排序 lint 问题，验证 Windows 本地及 GitHub Linux 的检查行为，不通过关闭整体 lint 规避。
- 同步 package.json、package-lock.json、README、CHANGELOG、项目索引至 1.4.1。
- 文档说明新错误字段、下载重试范围、超时预算、手动恢复方法及自动重试风险。
- 保持 release-it 的 npm.publish=false；npm 由维护者手动发布。

## 验证与验收

- 保留全部现有回归测试：模型列表、参数、Base64、URL、输出文件格式、item 关联。
- 下载首次失败后成功：生成 POST 恰好 1 次，下载 GET 次数正确。
- 重试耗尽：生成 POST 仍恰好 1 次，URL、错误阶段、各次诊断可恢复。
- 403、过期签名、无效 URL、HTML/JSON、空响应分别给出清楚的错误；不泄漏完整签名或凭据。
- 覆盖 Retry-After、时间预算及取消，不以真实长等待测试退避逻辑。
- 下载成功后 Binary 输出失败必须独立归类，不能误报下载失败或重新下载。
- 在 n8n 2.33.7 验证真实 helper 与执行错误序列化、错误详情展示；使用已有结果链接和受控响应，不以新付费生图作为默认验证手段。
- 本地测试/lint/build 通过后，先推送待发布代码并确认该提交远端 CI 通过，再用 release-it 创建版本 tag 和 GitHub Release，核对 tag、提交和更新说明一致。
